# 已运行测试的复检手册

版本：`review-v1` · 2026-10-22。

本手册统一程序检查、人工语义复检和报告生成的方法，适用于已有测试批次。
工具业务规则另读专项手册：[三个商品工具](tools/catalog/REVIEW.md)。
执行测试的入口与隔离要求见 [tests/README.md](README.md) 和 [仓库约束](../AGENTS.md)。
本手册不表示已有测试通过，也不授权重跑实验。

角色分工与测试分类以 [tests/README.md](README.md) 为入口。下文“人工语义复检”指
检查脚本之外的独立判读，可由人或LLM执行；必须在reviewer中明确实际身份。
LLM填写的记录应标为“独立LLM语义复检”，不能标为“人工已验收”。
技术通过与业务负责人实际审阅后的接受决定分别记录，不自动代签人工决定。

## 1. 新 session 的任务入口

可直接给执行者以下指令，替换批次路径：

```text
阅读 tests/REVIEW.md 和对应工具的 REVIEW.md。
复检指定批次：<批次路径>。
以该批次冻结的输入、预期、独立数据依据和实际调用/Trace为证据，
重新完成程序检查与独立语义复检，生成简洁 report.md。
只修改该批次的校验记录和报告，保留前次复检历史。
不重跑工具/模型，不重新查询业务数据库，不改用例预期、生产代码或脚本。
证据不足或标准不明确时如实记录，不用历史成绩补足。
```

默认读取本地已有证据。需要从原追踪平台补取记录时，先核对任务授权是否包含该只读访问；
用户已授权则直接继续，不重复询问。补取 Trace 不等于重新执行工具。
缺少结果文件时不得因“可以复现”自动发起收费或访问真实数据库的重跑。

## 2. 资料职责与判读依据

| 材料 | 用途 | 不能据此证明什么 |
| --- | --- | --- |
| 冻结用例及两类标注 | 确定目标、必要检查、比较方式、允许形式和失败标准 | 标注本身不能证明实际满足 |
| 独立数据依据及核对时间 | 确定身份、价格、数量、集合等事实预期 | 不能保证之后的数据一直不变 |
| 原始调用、输出、错误 | 说明工具实际收到了什么、返回了什么 | `ok=true` 不等于目标完成 |
| Trace | 说明实际规划、复核、校验和已采集的执行过程 | 不含未记录的SQL、逐行判断或隐藏推理 |
| 执行时源码/配置及指纹 | 解释当时契约和执行路径 | 实现行为不自动成为正确答案 |
| 旧检查和报告 | 对照判读差异、保留历史 | 不替代本次独立复检 |

业务预期依据运行前已确认要求与标注。文档和源码冲突时注明版本及差异，
不能把缺陷写成预期，也不能用当前源码覆盖执行时的行为解释。

运行前未明确的字段、等价形式或规则，不得在看到结果后随意补标准来决定通过或失败。
将额外发现记为观察；必要标准不足时判无法判定。若独立依据或预期本身有错，保留原值、
说明错误与影响；修订预期应另立版本，不能覆盖旧批次后改称原测试通过。

## 3. 按顺序复检

### 第一步：确定批次、授权和证据完整性

1. 确认用户指定的批次，读取工具专项手册；不混合不同批次或不同尝试。
2. 核对用例版本、执行时间、模型、HEAD、未提交源码指纹、脚本版本和运行方式。
   HEAD 相同但工作区不同不代表同一实现；哈希存在但源码已不可获取时注明解释限制。
3. 将每个用例与其输入、工具调用、尝试编号、Trace ID 对应；检查重复记录和缺失文件。
4. 核对独立预期是在执行前确定的，数据范围、快照/核对时间适用于本次调用。
   不使用本次被测返回值生成预期，不通过重新查当前数据库替代旧数据依据。
5. 分开记录：工具是否执行、业务是否满足、追踪是否完整。已知执行但输出丢失是证据缺口，
   不是“未执行”。只有记录证明未发起调用时才判未执行。

### 第二步：保存已有复检，再运行适用的程序检查

已有报告或校验记录时，在覆盖前将它们归档至该批次
`checks/history/<复检时间>/`，记录复检原因、准则版本和原文件哈希。
首次复检无需建立历史目录。只归档判读和报告，不复制整份原始 Trace。

检查脚本入口及副作用，确认它只读取证据并写分析文件，不隐式执行模型、数据库、服务启动
或依赖安装。对旧结果重新运行当前检查器前，应确认其比较规则与原标注兼容。
规则有变化时保留原检查结果并说明差异，不把新检查器输出伪装为旧脚本结果。

按每条预标注执行精确相等、集合相等、包含/排除、范围、顺序或允许形式等比较。
不精确匹配理由措辞、JSON键顺序等无关细节。金额遵守标注的单位与精度，
缺字段不能默认为零、空集合、否定或通过。

程序逐项记录：检查项、比较方式、预期、实际、结论。
检查器异常、取证失败和业务失败分别记录；脚本退出码不是验收结论。

### 第三步：独立语义复检

先读用户输入及运行前语义标注，再查看实际过程，不根据自动通过结果反推“理解正确”。
每条用例按以下顺序审查，仅应用本条适用的业务标准：

| 顺序 | 必须回答的问题 |
| --- | --- |
| 用户目标 | 用户想得到哪种结果？有没有遗漏、替换或拆错任务？ |
| 对象与范围 | 品牌、名称、编号、对象层级、可信范围是否保留？有无猜测身份或扩大范围？ |
| 条件与偏好 | 硬条件、软偏好、否定、单位、端点、AND/OR是否保留？有无新增限制？ |
| 事实询问 | 所问字段是否全部处理？是否误变为筛选？未知是否被当作否定？ |
| 执行与结果 | 实际结果和统计范围是否满足目标？有界展示是否被说成全集？ |
| 修正与证据 | 初始计划、后续修正、最终执行是否一致？结论是否有实际材料支持？ |

每个语义检查必须写：标注ID、通过/失败/无法判定、证据位置、简短理由。
证据引用应定位到文件、用例/尝试以及字段、Span ID或事件，不能只写“见Trace”。
说明为什么满足或违反标准，不仅复述模型的 approve。

逐次查看规划、复核和修正。初始错误若在执行前按既有预算修正，保留过程，但不能一概判失败；
是否要求一次正确由预标注决定。业务重跑的每次尝试均需保留并单独判断，不能只挑成功的一次。
程序与人工判断不一致时，显式记录两者结论、差异原因及最终依据。

### 第四步：确定状态并生成报告

| 最终状态 | 判定条件 |
| --- | --- |
| 通过 | 所有必要硬检查和语义检查通过，独立预期有效，必要证据充分 |
| 失败 | 已有明确的必要标准违反；其他缺证据部分仍逐项注明，不用它遮盖失败 |
| 无法判定 | 没有明确失败，但必要证据缺失、数据变化、标准不明或判读条件不足 |
| 未执行 | 确认未发起该用例调用，说明准备失败、覆盖缺口或其他原因 |

缺失 Trace 是否阻止通过，取决于本条预标注所需证据；不能一概忽略，也不能假装缺失内容存在。
某个检查不适用时保留适用性说明，不计作已通过项；不得为消除失败事后改成不适用。
本批所有用例都要有最终状态，统计不能漏掉失败、未执行和无法判定项。

## 4. 保存方式与简洁报告

通用约定如下；已有类型的具体文件格式以专项手册为准，不为遵守目录示意重构其他测试。

```text
<批次>/
  report.md                    # 默认阅读入口
  evidence/                    # 冻结输入、独立依据、环境、原始调用、原始Trace
  checks/
    automatic.jsonl            # 程序逐项比较
    semantic.jsonl             # 人工逐项判断
    history/<复检时间>/         # 仅重复复检时保留旧分析和报告
```

`report.md` 只有三个主要部分：

1. **本批结论**：范围、四种状态计数、主要发现；简记模型、用例/源码版本和批次。
2. **逐例结果表**：输入、关键预期→实际、程序结论、人工语义结论及一句理由、最终状态。
3. **问题与限制**：只展开失败、无法判定、未执行、判读分歧和重要观察；给出依据链接，
   说明影响与未覆盖范围。

通过项不展开几十个字段；不粘贴完整Prompt、JSON或Trace，不再生成逐例长Markdown报告。
底层证据只保存一份，程序和人工详细记录分别保存。核对报告与机器记录一致，证据链接有效。
数量来源观察、执行失败等已知问题不得因压缩报告而消失。

未来复检记录注明 `reviewer`、`reviewed_at`、准则版本（通用和专项）、批次/用例/Trace关联；
重复复检补充改判原因。历史记录未包含新元数据时不伪造其原始复检时间。
手册规则变化应更新版本并说明对既有批次的适用性，不自动改判历史结果。

## 5. 范围与结束检查

- 不修改冻结输入、原始输出或历史Trace；新取回的材料注明来源和取回时间。
- 不修改生产实现、Prompt、schema、埋点、数据库、默认测试保护，不在复检中修复缺陷。
- 不调用完整聊天流程替代单工具证据；不使用旧成绩、模型复核或Trace校验代替业务验收。
- 不把密钥、令牌、连接凭据或无关用户信息写进报告。
- results是忽略的本地产物。新session或新副本可能没有结果，缺失时明确说明；模型与动态数据
  变化使重跑不保证得到完全相同的结果，不能由重跑能力推断旧批次已经通过。
- 结束时只给报告链接、主要结论和必要限制；区分“重新分析旧结果”和“重新执行测试”。

复检可以写目标批次的分析和报告，这是任务本身；不能据此推断额外的实验或代码修改授权。
